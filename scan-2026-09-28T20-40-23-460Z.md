   ### Finding 4: Standard ERC20 allowance race on approve
   - Severity: informational
   - Confidence: high
   - Category: ERC20 semantics / user-safety
   - Affected functions: approve, increaseAllowance, decreaseAllowance, transferFrom
   - Root cause: ERC20 `approve` semantics are inherently racy for non-zero-to-non-zero changes. This is a known ERC20 interface issue, not an MGP-specific implementation bug.
   - Evidence: `_approve` directly sets `_allowances[owner][spender] = amount`. This follows the ERC20 standard. A spender can front-run an owner's `approve` transaction that changes a non-zero allowance to another non-zero value, spending the old allowance and then the new allowance.
   - Attacker capabilities: A malicious spender with an existing non-zero allowance can monitor the mempool and call `transferFrom` at the old allowance before the owner's new `approve` confirms.
   - Prerequisites: Owner uses `approve` to change an existing non-zero allowance to another non-zero value without first setting it to zero.
   - Exploit path: Owner submits approve(spender, newAmount). Spender front-runs with transferFrom(owner, attacker, oldAmount). Owner's approve sets newAmount. Spender then spends newAmount. The owner loses up to oldAmount + newAmount of spending permission, though tokens are only taken if the spender is malicious.
   - Invariant / assumption: The owner assumes changing allowance atomically revokes the old allowance. ERC20 does not guarantee this.
   - Impact: The spender can spend more than the owner intended when the owner changes an allowance directly. This is a well-known ERC20 user-safety issue, not a contract defect.
   - Exploitability: Real but user-dependent and standard across ERC20 tokens. Not specific to MGP.
   - Recommended fix: No contract change required for ERC20 compliance. Users should set allowance to zero before changing to a new non-zero value, or use `increaseAllowance`/`decreaseAllowance`. Integrators should prefer permit or exact-amount approvals.
